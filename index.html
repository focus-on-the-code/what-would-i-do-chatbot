01 · Executive Summary

Build a coach and thought partner, not a replacement.

This guide explains how to build a “What Would I Do?” chatbot: a coaching assistant that helps team members prepare for stronger conversations, recommendations, and decisions by reflecting a Team Leader’s known priorities, judgment, business context, and communication style.

Purpose

Improve preparation

Team members can pressure-test questions, ideas, and recommendations before bringing them to the Team Leader.

Approach

Use three focused phases

Scope the project, discover the source material, then build and test a small Claude-based V1.

Outcome

Prove V1 before scaling

Only move toward Slack, APIs, databases, or automation after the V1 prototype produces useful, grounded answers.

02 · What This Bot Is — and Is Not

A decision-prep simulator with clear boundaries.

The bot should help people think more clearly. It should not impersonate the Team Leader, invent missing context, or approve decisions.

It Is
It Is Not
A coach and thought partner
A decision maker
A way to pressure-test thinking before a conversation
A substitute for a real conversation when judgment is required
A guide that reflects known priorities, tone, and reasoning patterns
An impersonation of the Team Leader
A knowledge-and-judgment layer built from transcripts and business documents
A magic answer machine that invents missing facts
A tool for surfacing gaps, tradeoffs, and next steps
An approval workflow for budgets, hiring, strategy, or client commitments
03 · How the Idea Was Conceived

From one master prompt to a three-phase build process.

Start from scratch

Work with an LLM to define goals, ask discovery questions, identify source materials, and build a plan.

Start from transcripts

Use speaker-identified transcripts to extract the Team Leader’s reasoning, answers, feedback, and coaching style.

Simple path

Start quickly with a small source bundle, let Claude guide discovery, then test a manual V1 before broader rollout.

Current recommendation

The strongest structure is three separate work sessions: scoping, discovery, and tactical V1 build. Each phase has one job and creates a clear handoff to the next phase.

04 · The Three-Phase Build Model

Three chats. Three jobs. One clear handoff.

The build is best organized as three separate chats or work sessions, ideally inside the same Claude Project.

Phase 1

Scoping

Primary question: What are we building, for whom, and what does V1 need to prove?

Main work: Define project, end state, V1 scope, non-goals, success criteria, and V1.5–V4 roadmap.

Output: Project Scope Brief.

Phase 2

Discovery

Primary question: What source material should power the bot, and what does it tell us?

Main work: Review documents and transcripts, classify facts vs. judgment, rank transcripts, identify guardrails, gaps, and source hierarchy.

Output: Discovery Assessment.

Phase 3

Tactical V1 Build

Primary question: How do we turn the scope and discovery into a working Claude prototype?

Main work: Finalize source bundle, organize project knowledge, draft instructions, create verified test questions, and build the V1 testing process.

Output: Tactical V1 Build Package.

05 · Getting Started

Start with the workflow, not a perfect knowledge base.

The immediate move is not to build the whole system. It is to define scope, assess the best source material, build a small Claude-based V1, and verify answer quality.

Create or use a Claude Project.

Use it as the workspace for the three chats, uploaded documents, source review, and V1 prototype.

Run Phase 1 in a first chat.

Use the Scoping Prompt to define the project, V1 scope, non-goals, success criteria, and roadmap.

Upload or gather a starter source bundle.

Use a few relevant transcripts, current strategy or operating docs, and examples of strong feedback or decision-making.

Run Phase 2 in a second chat.

Use the Discovery Prompt to assess documents and transcripts, classify facts vs. judgment, and identify the best V1 source bundle.

Run Phase 3 in a third chat.

Use the Tactical V1 Build Prompt to assemble the Claude prototype, instructions, source bundle, and test plan.

Test V1 honestly before scaling.

Do not add Slack, APIs, databases, or automation until the simple prototype proves it can produce useful, grounded coaching responses.

Important note

If you stop at V1 — a shared Claude Project with custom instructions that responds to your team’s questions in your style — you may see all the value you need. V1.5–V4 increase durability, flexibility, and scalability, but they are not required to prove the concept.

06 · Build Roadmap

V1 through V4: scale only after the prototype works.

The roadmap shows how the system can mature after V1, but each stage should earn the right to exist.

V1
Manual Prototype Claude Project with curated docs, strong instructions, and a small test set.
1.5
Pre-launch Hardening Feedback loop, source cleanup, privacy review, and answer-quality scoring.
V2
Controlled Pilot Limited team access with clear usage expectations and ongoing refinement.
V3
Slack Deployment Slack bot connected to approved knowledge base using Anthropic API or orchestration layer.
V4
Maintained System Regular ingestion, review, governance, analytics, ownership, and version management.
07 · Recommended Tools

Claude first. Custom infrastructure later.

Best tools for V1

  • Claude Projects: best starting point because they allow curated project knowledge, custom instructions, and iterative testing without heavy engineering.
  • Claude chat: useful for scoping, source review, transcript analysis, prompt iteration, and test-question generation.
  • Document repository: controlled location for approved source-of-truth documents, transcripts, examples, and prompt versions.

Tools for later versions

  • Claude Code: useful later for scripted cleanup, transcript parsing, evaluation scripts, or Slack/API implementation.
  • Anthropic API: likely needed for V3 Slack deployment or a custom internal interface.
  • Retrieval layer/vector database: unnecessary for V1, potentially useful for V3/V4 if the source library becomes large or permission-aware retrieval is required.
08 · Three Reusable Phase Prompts

Use these prompts in sequence.

Each prompt has one focused job: scope, discover, or build. Run them as three separate chats or sessions inside the same Claude Project.

Prompt 1 · Phase 1 Scoping 
You are helping me scope a “What Would I Do?” chatbot for a team.

The goal is to create a chatbot that helps team members prepare for better conversations, recommendations, and decisions by giving coaching-style responses that reflect a Team Leader’s known priorities, judgment, reasoning patterns, business context, and communication style.

The chatbot should act as a coach and thought partner. It should not be a decision maker, should not replace the Team Leader, and should not pretend to be the Team Leader.

A good answer from the eventual chatbot should:
- identify the real issue behind the question,
- ask for missing context when needed,
- connect the issue back to team or business goals,
- give a practical next step,
- and sound like the Team Leader’s coaching style without impersonating them.

We are not building the chatbot yet. This is Phase 1: Scoping.

Your job in this phase is to help me define the project, clarify the end state, define a practical V1, and map a simple V1.5–V4 roadmap.

Work with me conversationally. Start by summarizing what you understand we are trying to build and why it matters. Then ask me one high-leverage question at a time.

Do not ask me for all details at once. After each answer I give, briefly summarize:
1. what you understood,
2. why it matters,
3. how it affects the scope,
4. and what question you need to ask next.

Focus your questions on:
- who will use the chatbot,
- what kinds of questions they should ask it,
- what decisions or topics it should not handle,
- what “good” would look like in V1,
- what business or team goals it should support,
- what level of confidence or authority it should avoid,
- what should be deferred until later versions,
- and what source materials will likely be needed in Phase 2.

Do not get deeply into document review yet. Do not try to select transcripts yet. Do not build final chatbot instructions yet. Those come later.

At the end of this phase, when you have enough information, produce a Project Scope Brief with these sections:

1. Project Definition
Explain what the chatbot is and why it exists.

2. Intended Users
Describe who the chatbot is for and how they are expected to use it.

3. Primary Use Cases
List the main kinds of questions or situations V1 should support.

4. V1 Scope
Define the simplest useful first version.

5. V1 Non-Goals
Define what V1 should not do.

6. Answer-Quality Standard
State what a good chatbot answer should include.

7. Initial Guardrails
List starting boundaries, including that the bot should not make decisions, approve commitments, impersonate the Team Leader, or give false confidence when evidence is weak.

8. Success Criteria
Define how we will know V1 is worth continuing.

9. V1.5–V4 Roadmap
Provide a simple roadmap:
- V1: manual/simple prototype
- V1.5: pre-launch hardening and feedback loop
- V2: team-facing controlled pilot
- V3: Slack or workflow deployment
- V4: maintained internal coaching system

10. Phase 2 Discovery Checklist
List the types of documents, transcripts, examples, and context we should review in the next phase.

Keep this practical for someone without a technical background. Favor the simplest useful path over a complex system design.
Prompt 2 · Phase 2 Discovery 
You are helping me build a “What Would I Do?” chatbot for a team.

We have completed Phase 1: Scoping. The project goal is to create a chatbot that helps team members prepare for better conversations, recommendations, and decisions by giving coaching-style responses that reflect a Team Leader’s known priorities, judgment, reasoning patterns, business context, and communication style.

The chatbot is a coach and thought partner. It is not a decision maker, not a replacement for the Team Leader, and should not pretend to be the Team Leader.

This is Phase 2: Discovery.

Your job in this phase is to review and assess the available source materials so we can decide what should power the V1 chatbot.

Do not build the chatbot yet. Do not write final chatbot instructions yet. Do not create the final test set yet. Those come in Phase 3.

Use the Phase 1 Project Scope Brief as the target for this discovery work. If I have not provided the Phase 1 brief yet, ask me to paste it before continuing.

I will provide or upload source materials such as:
- meeting transcripts,
- strategy documents,
- operating documents,
- product or project documents,
- customer context,
- decision notes,
- feedback examples,
- team communications,
- and other business context.

Your job is to help me inspect, classify, score, and prioritize these materials.

Work conversationally. Start by asking me what source materials are available or by reviewing the materials already uploaded. If more information is needed, ask one question at a time.

After each answer I give, briefly summarize:
1. what you understood,
2. why it matters,
3. how it affects the source-material plan,
4. and what you need to ask or review next.

Discovery goals:

1. Source Inventory
Create an inventory of available source materials. For each source, identify:
- source name or description,
- source type,
- likely usefulness,
- whether it supports facts, judgment, answer examples, guardrails, or testing,
- and any obvious sensitivity concerns.

2. Business and Team Context
Identify the best materials for factual context, including:
- company goals,
- team goals,
- product or service context,
- customer context,
- project priorities,
- operating principles,
- delivery expectations,
- current strategy,
- and any important constraints.

3. Team Leader Judgment and Style
Identify the best materials for judgment and coaching style, including:
- how the Team Leader thinks through problems,
- how they evaluate tradeoffs,
- how they define quality,
- how they push back,
- how they give feedback,
- how they coach,
- how they communicate expectations,
- how they handle incomplete information,
- and what patterns repeatedly show up.

4. Transcript Assessment
Do not simply ask me for “the best transcripts.” Help me create or review a transcript inventory and score candidate transcripts.

For each transcript, assess:
- whether speakers are identified,
- whether the Team Leader’s comments are easy to isolate,
- whether it includes useful coaching, feedback, decision reasoning, prioritization, or tradeoff analysis,
- whether it includes current business context,
- whether it reflects reusable judgment patterns rather than one-off comments,
- whether it is recent enough to rely on,
- whether it contains sensitive material that should be excluded, redacted, or handled carefully,
- and whether it supports the V1 use cases from the Phase 1 scope.

Score each transcript as:
- High value for V1,
- Medium value for V1,
- Low value for V1,
- Exclude from V1,
- or Needs review/redaction.

5. Facts vs. Judgment Classification
Classify the useful source material into:
- Facts: company, team, product, customer, project, strategy, operating, and delivery context.
- Judgment: how the Team Leader thinks, coaches, evaluates tradeoffs, pushes back, defines quality, processes information, and gives feedback.
- Answer examples: specific examples of strong responses or coaching moments the bot should learn from.
- Guardrails: topics, risks, privacy issues, or sensitive areas the bot should avoid or handle carefully.
- Gaps: missing information needed to make V1 useful.

6. Source-of-Truth Hierarchy
Recommend a source-of-truth hierarchy for V1. When sources conflict, explain which sources should carry more weight and why. Do not silently resolve important conflicts. Surface them.

Use this starting hierarchy unless the source materials suggest a better one:
1. Current strategy, operating principles, and formal company direction.
2. Current product, project, customer, and roadmap documents.
3. Recent meeting transcripts with speaker identification, especially the Team Leader’s answers and feedback.
4. Older transcripts and historic context.
5. Inferred coaching style, reasoning patterns, and tone guidance derived from examples.

7. Guardrails and Sensitivity Review
Identify any additional do-nots or guardrails suggested by the source material. Pay special attention to:
- HR or personnel topics,
- legal or financial issues,
- compensation,
- client commitments,
- confidential strategy,
- sensitive customer information,
- performance feedback,
- role-based access concerns,
- and places where the bot might overstate confidence.

8. Missing Materials
Identify what is missing for V1. Be practical. Do not ask for a perfect knowledge base. Separate missing materials into:
- required for V1,
- useful but optional for V1,
- safe to defer to V1.5 or later.

9. Recommended V1 Source Bundle
Recommend the smallest useful source bundle for V1. Include:
- must-have documents,
- best transcripts,
- answer-example candidates,
- any sources that need cleanup or redaction,
- and sources to exclude for now.

At the end of Phase 2, produce a Discovery Assessment with these sections:

1. Summary of What Was Reviewed
2. Recommended V1 Source Bundle
3. Source Inventory
4. Transcript Ranking
5. Facts Map
6. Judgment and Coaching Style Map
7. Answer Example Candidates
8. Guardrails and Sensitivity Notes
9. Source-of-Truth Hierarchy
10. Missing Materials
11. Open Questions Before Build
12. Handoff Notes for Phase 3

Keep this practical for someone without a technical background. Your goal is to help us choose and organize the right source materials for V1, not to design a complex technical system.

- who it is for,
- what it will not do,

2. Finalize the V1 Source Bundle

Review the recommended source bundle from Phase 2 and produce a final upload checklist.

Include:
- must-have documents,
- useful optional documents,
- transcripts to include,
- transcripts to exclude,
- sources that need cleanup or redaction,
- sources that should be excluded from V1,
- and any missing materials that should not block V1.

Keep the source bundle as small as possible while still making V1 useful and testable.

3. Prepare Source Organization

Recommend a simple document organization method for Claude Project knowledge.

Use categories such as:
- 00_Project_Scope
- 01_Current_Strategy_and_Context
- 02_Product_Project_Customer_Context
- 03_Team_Operating_Context
- 04_Team_Leader_Judgment_and_Coaching
- 05_Transcript_Excerpts
- 06_Answer_Examples
- 07_Guardrails_and_Do_Nots
- 08_Test_Set

Keep this simple. Do not recommend complex databases, embeddings, APIs, or Slack integration for V1 unless absolutely necessary.

4. Define Confidence Modes

Define the confidence modes the V1 chatbot should use before answering.

Include these four response modes:

Strong-context answer:
Use when current, relevant source material clearly supports the response and there is no obvious conflict. The bot may give direct guidance, while making clear that the answer is based on available context and is not a final decision.

Partial-context answer:
Use when some relevant context exists but important details are missing. The bot should state what is known, name what is missing, frame the issue, and suggest a practical next step.

Insufficient-context answer:
Use when the source material does not support a confident answer. The bot should say there is not enough evidence to answer directly, then help the user clarify the question or prepare the issue.

Conflicting-context answer:
Use when sources point in different directions. The bot should name the conflict, identify which source appears more current or reliable, and frame the tradeoff without pretending the issue is settled.

The bot should always match confidence to evidence and should not give false confidence when evidence is weak.

5. Define Decision-Boundary Rules

Decision-boundary rules define the bot’s role and authority. They keep the bot acting as a coach and thought partner, not as the Team Leader or as an approval authority.

The chatbot may:
- help frame decisions,
- identify tradeoffs,
- clarify missing context,
- connect issues to team or business goals,
- suggest practical next steps,
- pressure-test assumptions,
- help users prepare stronger recommendations,
- and explain what a stronger decision conversation should include.

The chatbot must not:
- make final decisions,
- approve or reject decisions,
- approve budgets, hiring, compensation, client commitments, roadmap changes, strategy shifts, or personnel decisions,
- speak as the Team Leader,
- write in first person as if it is the Team Leader,
- imply the Team Leader approved, decided, or endorsed something unless the source material explicitly says so,
- or treat coaching output as authority.

When a question asks for a decision, approval, or commitment, the bot should reframe its answer as decision preparation. It should say what needs to be clarified, what tradeoffs matter, and what a strong recommendation should include.

6. Define Guardrails and Do-Nots

Guardrails and do-nots define the bot’s risk, source-use, privacy, and quality limits. They prevent the bot from mishandling sensitive, unsupported, outdated, private, or risky information.

Create a clear Guardrails and Do-Nots section for the V1 chatbot instructions.

Avoid duplicating the decision-boundary rules. Decision-boundary rules are about the bot’s authority. Guardrails and do-nots are about safe, accurate, private, and appropriate use of the knowledge base.

Start with these baseline do-nots:

Source and grounding rules:
- Do not invent company, team, customer, product, project, strategy, or operating context if the source material does not support it.
- Do not give false confidence when evidence is weak.
- Do not treat casual transcript comments as formal policy unless confirmed by current source-of-truth documents.
- Do not rely on outdated sources without clearly saying the context may be outdated.
- Do not silently resolve important conflicts between sources. Surface the conflict and explain what would need to be clarified.
- Do not use excluded sources or sources marked as requiring review/redaction.

Privacy and sensitivity rules:
- Do not quote or reveal sensitive transcript details unless those details are appropriate for the intended audience.
- Do not expose private personnel feedback, confidential client context, restricted business information, compensation details, or sensitive performance-related content.
- Do not answer sensitive HR, legal, financial, compensation, performance, or confidential questions as if the chatbot has authority or complete context.
- Do not turn private or situational comments from transcripts into general guidance unless they are supported by approved source material.

Topic and usage limits:
- Do not provide authoritative guidance on topics that Phase 2 marked as excluded, sensitive, outdated, or outside V1 scope.
- Do not expand beyond the V1 use cases unless clearly labeled as general thinking support rather than grounded Team Leader-style guidance.
- Do not present unsupported speculation as Team Leader judgment.

Then review the Phase 2 Discovery Assessment and add any source-specific do-nots based on:
- sensitive topics found in the materials,
- excluded documents or transcripts,
- role-access concerns,
- privacy risks,
- conflicting sources,
- outdated guidance,
- customer or client confidentiality,
- personnel or performance content,
- legal, financial, or compliance sensitivity,
- and areas where the chatbot is likely to overstate confidence.

Separate the final guardrails into these categories:
1. Source and grounding rules
2. Privacy and sensitivity rules
3. Topic exclusions
4. Source-use restrictions
5. Confidence and uncertainty rules

For each guardrail, briefly explain why it matters and how the chatbot should behave instead.

7. Define Source-of-Truth Behavior

Using the Phase 2 Discovery Assessment, define how the chatbot should decide which sources to rely on.

Include:
- which sources should carry the most weight,
- how current formal documents should be treated compared with older transcripts,
- how recent transcripts should be used,
- how inferred coaching patterns should be used,
- and how the bot should behave when sources conflict.

Use this starting hierarchy unless Phase 2 suggests a better one:
1. Current strategy, operating principles, and formal company direction.
2. Current product, project, customer, and roadmap documents.
3. Recent meeting transcripts with speaker identification, especially the Team Leader’s answers and feedback.
4. Older transcripts and historic context.
5. Inferred coaching style, reasoning patterns, and tone guidance derived from examples.

The bot should not silently resolve major conflicts. It should surface the conflict and explain what would need to be clarified.

8. Draft V1 Chatbot Instructions

Now synthesize the prior sections into a clean set of V1 chatbot instructions.

These instructions should be usable as Claude Project instructions or pasted into a prototype chat.

The instructions should include:
- role and purpose,
- intended users,
- answer-quality standard,
- how to use the uploaded knowledge,
- facts vs. judgment behavior,
- confidence modes,
- decision-boundary rules,
- guardrails and do-nots,
- source-of-truth behavior,
- how to handle missing context,
- how to handle conflicting sources,
- how to avoid impersonating the Team Leader,
- and the preferred response structure.

The instructions should be clear, practical, and not overly long. They should be specific enough to guide the chatbot’s behavior, but not so long that they become hard to maintain.

9. Create the V1 Test Plan

Create a testing plan using 10–20 questions with verifiable answers based on the selected source material.

Do not create generic test questions only. The questions should be grounded in the actual Phase 1 and Phase 2 materials.

Organize test questions into categories such as:
- business context,
- product or project priorities,
- team operating expectations,
- customer or stakeholder tradeoffs,
- Team Leader coaching style,
- decision-prep scenarios,
- missing-context scenarios,
- conflicting-source scenarios,
- guardrail/sensitive-topic scenarios,
- unsupported-question scenarios.

For each test question, include:
- the question,
- what source material should support the answer,
- what a strong answer should include,
- what failure would look like,
- and which rubric criteria matter most.

10. Create Verified Answer Notes

Help me create verified answer notes for the test set.

If the sources already support the answer, summarize the expected answer.

If the answer cannot be verified from the sources, label it as not verifiable and recommend whether to:
- remove the question,
- add source material,
- rewrite the question,
- or use it as an insufficient-context test.

11. Create Evaluation Rubric

Use this rubric unless the Phase 1 or Phase 2 outputs suggest changes:

- Grounding: Is the answer supported by the provided materials?
- Real issue: Did it identify the real underlying issue?
- Missing context: Did it ask for or name missing information when needed?
- Goal connection: Did it connect the answer to team or business goals?
- Practical next step: Did it give a clear next action?
- Team Leader-style coaching: Did it reflect the Team Leader’s reasoning and coaching style without impersonating them?
- Confidence discipline: Did it avoid false confidence?
- Decision boundary: Did it avoid acting as a decision maker?
- Guardrail discipline: Did it avoid mishandling sensitive, unsupported, outdated, excluded, or private information?

Score each criterion from 1 to 5.

Conflicting Context

Use when sources point in different directions.

Decision-Boundary Rules

  • The chatbot may help frame decisions, identify tradeoffs, clarify missing context, and suggest next steps.
  • The chatbot must not make final decisions or approve budgets, hiring, compensation, client commitments, roadmap changes, strategy shifts, or personnel decisions.
  • The chatbot must not speak as the Team Leader or imply approval unless the source material explicitly says so.

Guardrails and Do-Nots

  • Do not invent context, overclaim, treat casual transcript comments as policy, or use excluded/redaction-required sources.
  • Do not reveal sensitive transcript details, private personnel feedback, confidential client context, compensation details, or sensitive performance content.
  • Do not present unsupported speculation as Team Leader judgment.

A4 · Source-of-Truth Behavior

Current formal sources should outweigh old or casual comments.

  • Current strategy, operating principles, and formal company direction.
  • Current product, project, customer, and roadmap documents.
  • Recent meeting transcripts with speaker identification, especially the Team Leader’s answers and feedback.
  • Older transcripts and historic context.
  • Inferred coaching style, reasoning patterns, and tone guidance derived from examples.

When sources conflict, the bot should not silently resolve major conflicts. It should surface the conflict and explain what needs clarification.

A6 · Pitfalls, Alternatives, and Tradeoffs

Avoid overbuilding before proving the idea.

Key Pitfalls

  • Overbuilding too early, especially jumping to Slack before proving answer quality.
  • Dumping too many raw transcripts into the bot without curation or source hierarchy.
  • Tone-matching without judgment.
  • False confidence when evidence is weak.
  • No test set, which makes improvement subjective and hard to measure.

Alternatives

  • Start with a written operating manual instead of a chatbot, then turn that manual into a bot later.
  • Create a library of Team Leader-style coaching examples and decision frameworks before adding transcripts.
  • Build a narrow bot focused on one team or one workflow first, then expand.
  • Use the bot only as a preparation checklist generator, not as a Q&A assistant.

Core Tradeoffs

  • Manual V1 is faster but less scalable.
  • Transcript-heavy sources are authentic but noisy.
  • Broad team bots are useful but harder to govern.
  • Source citations add transparency but may expose sensitive context or feel less natural.
Final Takeaway

Start small, test honestly, and only scale what works.

The immediate move is not to build the whole system. It is to define the scope, assess the best source material, build a small Claude-based V1, and verify whether the chatbot produces useful, grounded coaching responses before expanding.
